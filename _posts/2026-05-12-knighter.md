## Summary for KNighter: Transforming Static Analysis withLLM-Synthesized Checkers

## Introduction
커널과 같은 기반 소프트웨어의 신뢰성은 결함을 잡아내는 방법론에 크게 좌우되는데, 그중 **정적 분석(static analysis)** 은 코드를 실행하지 않고 소스코드를 검사할 수 있어, 하드웨어 의존적 드라이버나 복잡하고 거의 실행되지 않는 경로, 실제 환경에서 재현하기 어려운 설정 등을 분석하는 데 특히 유용합니다. <br>
![k_1](/assets/img/posts/papers/knighter_1.png) <br>

위 그림에서 확인할 수 있듯이, 대규모 시스템의 정적 분석에는 두 가지 과제가 있습니다: 다양한 버그 패턴을 다루는 것과 거대한 코드베이스를 처리하는 것입니다. 이상적인 정적 분석기는 i) 시스템 고유의 세밀한 시멘틱 관련 결함을 포함해 광범위한 버그를 탐지하고, ii) 수백만 줄의 소스코드를 효율적으로 처리해야 합니다. 그러나 기존 방법들은 이 두 목표 중 하나를 희생하는 경향이 있습니다.

**전통적 정적 분석** 은 사전 정의된 규칙 기반 검사에 의존하므로 도메인 전문 지식과 상당한 엔지니어링 노력이 필요하며, 결과적으로 좁은 범위의 버그 패턴에만 대응할 수 있습니다. 반면 **LLM 기반 정적 분석** 은 과거 패치 커밋에서 직접 버그 패턴을 학습할 수 있지만, 제한된 컨텍스트 윈도우와 높은 연산 비용, 그리고 환각(hallucination) 문제로 인해 대규모 시스템에 직접 적용하기 어렵습니다.

본 논문에서는 LLM으로 코드베이스 전체를 직접 분석하는 대신, **LLM을 이용하여 static checker를 합성** 하는 방식을 제안합니다. LLM은 이전 패치들로부터 버그 패턴을 학습하고, 학습된 패턴은 독립적으로 실행 가능한 정적 체커로 인코딩됩니다. 이를 통해 LLM의 시멘틱 이해 능력은 체커 생성 시점에만 활용하고, 실제 코드베이스 스캔은 합성된 체커가 결정론적으로 수행하므로 컨텍스트 길이와 비용 문제를 동시에 해결합니다. 환각(hallucination) 문제 역시 구조적으로 대응하는데, 합성된 체커를 원본 패치 이전 코드에 실행하여 해당 버그를 실제로 탐지하는지 ground truth로 검증함으로써, LLM이 만들어낸 규칙이 실제 버그 패턴과 정확히 대응되는지 확인할 수 있습니다.

그러나 완전한 정적 분석 로직을 한 번에 합성하는 것은 상당한 난이도를 갖기 때문에, 본 논문에서는 **multi-stage synthesis pipeline** 을 구성하여 체커 생성을 단계별로 분할하고, **fully automated refinement pipeline** 을 통해 체커의 품질을 반복적으로 향상시키며 false positive를 줄입니다.

이러한 방법론을 적용하여 만든 **KNighter** 는 `Clang Static Analyzer(CSA)` 를 기반으로 리눅스 커널을 대상으로 합니다. KNighter는 평균 4.3년간 잠복해 있던 92개의 새로운 버그를 발견하였으며, 이 중 77개가 확인되고 57개가 수정되었고, 30개의 CVE를 발급받았습니다.

## Background and Motivation
### Clang Static Analyzer
Clang Static Analyzer(CSA)는 C/C++/Objective-C를 대상으로 하는 정적 분석 엔진으로, 내부적으로 `ExplodedGraph`를 구축하여 **path-sensitive symbolic execution** 을 수행합니다. ExplodedGraph의 각 노드는 프로그램의 특정 지점(ProgramPoint)과 그 시점의 추상 상태(ProgramState)의 쌍으로 구성되며, 분기마다 경로가 독립적으로 탐색됩니다.

CSA의 핵심 설계는 **분석 엔진과 탐지 로직의 분리** 에 있습니다. 경로 탐색, 기호 실행, 메모리 모델링은 엔진이 담당하고, 개별 버그 패턴의 탐지는 **체커(checker)** 라는 독립된 플러그인이 담당합니다. 체커는 함수 호출 전후, dead symbol 식별, 포인터 탈출 등 특정 분석 이벤트에 대한 콜백을 등록하는 이벤트 기반 구조로, 새로운 버그 패턴을 추가할 때 엔진 자체를 수정할 필요 없이 체커만 작성하면 됩니다. 체커 개발은 i) 탐지할 버그 패턴 정의, ii) 해당 이벤트에 대한 콜백 구현, iii) 프레임워크에 체커 등록, iv) 테스팅 시스템 통합의 단계로 이루어집니다. <br>

![k_2](/assets/img/posts/papers/knighter_2.png) <br>

위의 예시 체커는 4개의 콜백 함수를 등록하고 있습니다. `checkPostCall` 콜백은 함수 호출 후에 활성화되며, `ExprHasName`을 이용하여 호출이 `devm_kzalloc`으로 이어지는지 확인하고, 맞다면 반환된 메모리 영역을 커스텀 상태 맵 `PossibleNullPtrMap`에 unchecked(`false`)로 기록합니다. `checkBranchCondition` 콜백은 분기 조건에서 해당 포인터에 대한 null 체크가 수행되는지를 감시합니다. `if (!ptr)` 형태의 부정 연산자 패턴과 `if (ptr == NULL)` 또는 `if (ptr != NULL)` 형태의 직접 비교 패턴을 인식하며, 이러한 조건이 확인되면 `markRegionChecked`를 호출하여 해당 메모리 영역의 상태를 checked로 갱신합니다. `checkLocation` 콜백은 메모리 위치에 대한 접근이 발생할 때 트리거되며, `PossibleNullPtrMap`에서 해당 영역이 여전히 unchecked 상태인지 조회합니다. unchecked 상태인 포인터가 역참조되고 있다면 `reportUncheckedDereference`를 통해 경고를 발생시킵니다. 마지막으로 `checkBind` 콜백은 포인터 대입 연산을 처리합니다. `ptr_b = ptr_a`와 같은 대입이 일어나면 `PtrAliasMap`에 양방향으로 앨리어싱 관계를 기록하여, 원본 포인터가 다른 변수로 복사되더라도 null 체크 상태를 놓치지 않도록 추적을 유지합니다.

### Motivating Example
![k_3](/assets/img/posts/papers/knighter_3.png) <br>

위 패치는 `devm_kzalloc` 함수 호출 후 null 포인터 체크 누락으로 인한 Null-Pointer-Dereference 취약점을 수정하는 패치입니다. Smatch와 같은 커널 특화 체커를 포함한 기존 정적 분석 도구들은 `devm_kzalloc`이 실패 시 NULL을 반환할 수 있다는 도메인 지식이 없어 이 유형의 버그를 탐지하지 못했습니다. KNighter는 이 패치로부터 **devm_kzalloc의 반환값이 NULL인지 확인하지 않으면 Null-Pointer-Dereference로 이어질 수 있다는 핵심 패턴** 을 추출하고, 합성된 체커는 실행 경로를 따라가며 null 체크 여부를 추적하고 포인터 앨리어싱까지 처리합니다. 이 체커를 통해 리눅스 커널에서 3개의 새로운 취약점을 발견했으며, 그중 하나는 CVE-2024-50103으로 지정되었습니다.

LLM을 이용하여 커널을 직접 스캐닝하는건 굉장히 비싼 작업이 될 수 있지만, KNighter 정적 분석은 LLM을 반복해서 호출하는 것보다 훨씬 자원 소모가 덜하다고 볼 수 있습니다. LLM을 이용하여 효과적인 체커를 생성하기 위해 여러 단계로 이뤄진 파이프라인을 구성하여 체커를 생성하고, 패치 기록과 비교하여 실제로 유의미한 체커가 만들어진게 맞는지 확인합니다.

## Design
KNighter는 패치 커밋을 입력으로 받아 대응되는 CSA 체커를 반환합니다. `Valid Checker`는 버그가 있는 코드와 패치된 코드를 올바르게 구별하고, 패치 전 코드를 결함 상태로 판단하고 패치된 코드를 올바르다고 판단합니다. `Plausible checker`는 valid checker 중에서도 실용적 가치(낮은 오탐률, 리포트 수)까지 갖춘 체커를 의미합니다. <br>

![k_4](/assets/img/posts/papers/knighter_4.png) <br>

KNighter는 위 그림에 나와 있는 것처럼 에이전틱 워크플로우를 활용하여 패치 커밋으로부터 정적 분석기를 합성합니다. 크게 `Checker Synthesis`와 `Checker Refinement` 두 단계로 나뉩니다. 합성 단계에서는 입력 패치를 분석하여 버그 패턴을 식별하고, 탐지 계획을 수립한 뒤 CSA 체커를 구현합니다. 컴파일 에러가 발생하면 syntax-repair 에이전트가 컴파일러 에러 메시지를 기반으로 자동 수정합니다. 이 과정을 통해 `valid checker`가 생성되면 정제 단계로 넘어갑니다. 정제 단계에서는 valid checker로 전체 커널을 스캔하여 버그 리포트를 생성하고, triage agent가 각 리포트의 오탐 여부를 판별합니다. 오탐으로 식별된 케이스는 refinement agent에 피드백되어 체커 로직을 반복적으로 개선합니다. 최종적으로 낮은 오탐률을 보이거나 일정 수 이하의 리포트만 생성하는 체커를 **plausible checker** 로 분류합니다.

### Checker Synthesis
![k_5](/assets/img/posts/papers/knighter_5.png) <br>

위 알고리즘은 multi-stage 체커 합성 파이프라인을 나타냅니다. 버그 패턴 분석, 합성 계획 수립, 체커 구현, 문법 수정(5번까지), 체커 유효성 확인 단계로 이뤄집니다. 

#### Bug Pattern Analysis
![k_6](/assets/img/posts/papers/knighter_6.png) <br>

패치 커밋은 주로 `diff` 패치와 수정될 버그를 설명하는 개발자 코멘트로 구성이 되는데, 이 단계에서의 목표는 정적 분석 규칙으로 변환될 수 있는 패턴을 추출하는 것입니다. 본 논문에서는 위와 같은 프롬프트 템플릿을 이용하여 패턴 분석에 특화된 LLM 에이전트를 개발하였습니다. 또한 커널 코드로부터 수정된 함수 코드 전체를 추출하여 `diff`만으로는 부족할 수 있는 추가적인 컨텍스트를 제공합니다. 

하나의 패치에서 추출한 버그 패턴은 **범위와 복잡도를 다르게** 표현할 수 있는데, 이전의 `devm_kzalloc` 예시로 설명하면 **넓은 패턴** 은 NULL을 반환할 수 있는 모든 함수의 반환값을 체크하는 방식이고, **좁은 패턴** 은 구체적으로 devm_kzalloc 함수의 반환값이 NULL인지 체크하는데 집중하는 방식입니다. KNighter는 좁은 패턴을 이용하여 LLM이 정확하게 구현하기 쉽게 만들고 효과적으로 버그 클래스를 잡아냅니다.

#### Plan Synthesis
버그 패턴이 식별되면 KNighter는 정적 분석기 구현을 위한 **고차원 계획** 을 생성합니다. 이 계획은 두 가지 목적을 갖습니다. 첫째, LLM에게 구조화된 가이던스를 제공하여 혼란과 환각을 방지하는 것이고, 둘째, LLM의 추론 과정을 투명하고 추적 가능하게 만들어 전체 파이프라인의 디버깅을 용이하게 하는 것입니다. 예를 들어 `devm_kzalloc` 반환값에 대한 체커를 합성할 때 다음과 같은 계획을 생성할 수 있습니다.

1. 프로그램 상태를 이용하여 `devm_kzalloc`으로부터 할당된 메모리 영역을 추적
2. 조건 분기(`checkBranchCondition`)를 모니터링하여 null 체크가 발생하면 해당 영역을 checked로 표시
3. 체크되지 않은 영역에 대한 접근(`checkLocation`)이 발생하면 잠재적 버그로 경고

![k_7](/assets/img/posts/papers/knighter_7.png) <br>

이러한 구현 계획을 합성하기 위해 위와 같은 프롬프트 템플릿을 설계하였습니다. 이 에이전트는 앞서 **요약된 버그 패턴** 을 입력으로 받으며, 추가로 체커 구현에 활용 가능한 유틸리티 함수들의 시그니처와 간략한 설명을 프롬프트에 포함시켜 LLM이 계획 수립 과정에서 이를 효과적으로 활용할 수 있도록 합니다.

#### Analyzer Implementation and Syntax Repair
![k_8](/assets/img/posts/papers/knighter_8.png) <br>

버그 패턴을 식별하고 계획을 수립한 후, LLM 에이전트를 활용하여 체커를 구현합니다. 구현 정확도를 높이기 위해 에이전트에게 추출된 버그 패턴, 구조화된 구현 계획과 함께 위와 같은 미리 정의된 체커 템플릿을 제공합니다. 이 템플릿은 구현 구조를 표준화하여 잠재적 오류를 줄여줍니다. 또한 구현에 도움이 될 수 있는 유틸리티 함수 목록도 함께 제공됩니다.

합성된 체커에는 잘못된 API 사용이나 부정확한 변수 타입 등의 컴파일 에러가 발생할 수 있습니다. 이를 처리하기 위해 전용 디버깅 에이전트를 사용하여 컴파일러 에러 메시지를 자동으로 분석하여 필요한 수정을 적용하며, 최대 5회까지 수리를 시도합니다. 이 자동화된 디버깅 파이프라인을 통해 최종 체커가 구문적으로 올바르고 컴파일 가능한 상태임을 보장합니다.

#### Validation
체커가 의미론적으로 올바른지 확인하기 위해 패치 전 코드와 패치된 코드에 대해 평가를 합니다. 만약 패치 전 코드에 대해서는 버그가 있음을 나타내고, 패치된 버전에서는 버그가 사라졌다는 걸 구분해내면 체커를 **valid** 하다고 간주합니다.

### Checker Refinement
합성 이후 valid 체커들을 전체 시스템에 대해 스캔하는데, 초기 검증은 패치 전후 코드만을 대상으로 하므로 더 넓은 코드베이스에서는 오탐이 발생할 수 있습니다. 이를 완화하기 위해 생성된 버그 리포트를 평가하고, 식별된 오탐을 피드백하여 체커를 반복적으로 정제하는 LLM 기반 정제 절차를 구현하였습니다. 그러나 이 정제를 자동화하는 데에는 두 가지 장애물이 있습니다. 첫째, 버그 리포트가 방대한 컨텍스트를 포함하고 있어 효율적으로 처리하기 어렵고, 둘째, 오탐에 기반하여 체커 로직을 디버깅하고 수정하는 것 자체가 복잡한 분석을 요구합니다. <br>

![k_9](/assets/img/posts/papers/knighter_9.png) <br>

KNighter의 정제 파이프라인은 이 문제들을 체계적으로 해결합니다. 리포트가 장황한 문제에 대해서는 **리포트를 핵심 요소만 남기도록 압축** 하여, 정적 분석기가 강조한 관련 코드 라인과 실행 경로(trace path)만 추출합니다. 분석과 수정의 복잡성에 대해서는 특화된 LLM 에이전트를 활용하는데, triage agent가 압축된 각 리포트를 분류하며 일반적인 코드 정확성이 아닌 **목표 버그 패턴과의 일치 여부** 에만 초점을 맞춥니다. 프롬프트 템플릿은 위와 같습니다. <br>

![k_10](/assets/img/posts/papers/knighter_10.png) <br>

위처럼 triage agent가 리포트를 false positive로 식별하면, 전용 정제 에이전트가 이를 넘겨받습니다. 그림의 사례에서 체커는 `pmx->pfc` 사용을 버그로 잡아내고 있지만, 실제로는 `if (unlikely(!pmx))` 구문에서 이미 null 체크가 수행되고 있습니다. 체커가 `unlikely()` 매크로를 유효한 null 체크로 인식하지 못한 것이 원인입니다. triage agent는 이를 의미론적으로 올바르게 해석하여 FP로 표시하고, 정제 에이전트는 이 정보를 활용하여 `unlikely()` 같은 구문도 처리할 수 있도록 체커 로직을 수정합니다. 정제된 체커는 두 가지 조건을 모두 만족할 때만 수용됩니다: i) 이전에 식별된 오탐 사례에 대해 더 이상 경고를 생성하지 않으며, ii) 원래의 버그 코드와 패치된 코드를 여전히 정확하게 구별할 수 있어야 합니다.

## Implementation
### Input commit collection
패치 커밋 수집을 위해 10개의 버그 카테고리를 설정하고, 관련 키워드로 커밋을 검색하였습니다. 두 명의 저자가 독립적으로 동일하게 분류한 커밋만 데이터셋에 포함하며, 버그 타입당 최소 5개 커밋 확보를 목표로 하였습니다.

### Few-shot examples
In-context 학습을 위해 Null-Pointer Dereference, Use-Before-Initialization, Double-Free 3가지 패치에 대한 체커를 직접 구현하여 예제로 사용하였으며, 약 40 person-hour가 소요된 일회성 작업입니다.

### Utility functions
예제 체커 구현 과정에서 `getMemRegionFromExpr` 등 9개의 공통 유틸리티 함수를 식별하여 구현하였습니다. 이는 저수준 CSA 작업을 캡슐화하여 LLM의 체커 합성을 단순화합니다.

### Valid checkers
체커의 유효성은 원래 버그를 탐지하면서 동시에 수정된 코드를 정상으로 인식하는지를 통해 검증합니다. 먼저 diff 패치에서 수정된 파일들을 확인하여 buggy object를 식별합니다. 그 다음 패치 직전 커밋으로 체크아웃하여 해당 객체들을 스캔하고 버그 리포트 수($N_buggy$)를 셉니다. 이후 패치를 적용한 상태에서 동일한 객체들을 다시 스캔하여 남은 리포트 수($N_patched$)를 얻습니다. 체커는 $N_buggy$ > $N_patched$이고 $N_patched$ < $T_valid$ (기본값 50)일 때 유효한 것으로 판정됩니다. 즉, 패치 전에는 버그를 잡아내되 패치 후에는 경고가 줄어들어야 하며, 패치 후에도 과도한 리포트를 생성하지 않아야 합니다.

### Plausible checkers
전체 커널 스캔 시 리포트가 임계값(기본 20) 미만이거나, 샘플링된 경고 중 오탐이 1개 이하인 체커를 plausible로 분류합니다. 기준을 충족하지 못하면 최대 3회까지 정제를 반복합니다.

## Evaluation
본 연구에서는 KNighter에 대한 4개의 research question에 대하여 탐구를 진행하였습니다.

1. **RQ-1:** KNighter가 고품질 체커를 생성할 수 있는가?
2. **RQ-2:** KNighter가 생성한 체커들이 실제로 커널에서 버그를 발견할 수 있는가?
3. **RQ-3:** KNighter의 성능이 사람이 작성한 체커가 잡아내지 못하는 버그를 발견할 수 있는가?(직교)
4. **RQ-4:** KNighter의 핵심 구성요소들이 효과적인가?

본 논문에서는 5가지 평가 지표를 사용합니다.

#### Checker Validity Rate
Valid checker가 생성된 비율로, 패치를 의미론적으로 이해하고 체커를 합성하는 프레임워크와 LLM의 능력을 나타냅니다.

#### Plausible Checker Rate
`Valid`하면서 낮은 false positive 비율을 보이는 고품질 체커 수를 나타냅니다.

#### Bug Detection
생성된 체커를 통해 실제로 발견해낸 real-world 버그 수를 평가한 것입니다.

#### Resource Efficiency
체커 합성, 실행에 소요된 계산 시간과 금전적 비용을 나타냅니다.

#### Checker Error categories
체커 생성 실패를 심각도 순으로 세 가지로 분류합니다. 첫째는 컴파일 에러, 둘때는 Runtime error(컴파일은 됐지만 실행 중 크래시), Semantic Issue(실행은 되지만 버그가 있는 코드를 구별못함)

### RQ1: Synthesized Checkers

#### Checker Synthesis
61개 커밋 중 39개(64%)에 대해 valid checker가 생성되었으며, 평균 125.7줄의 코드로 구성됩니다. 37개가 path-sensitive 분석을 수행하고 16개가 고급 상태 추적을 사용하는 등 단순 패턴 매칭을 넘어서는 복잡한 분석 로직을 갖추고 있습니다. 전체 합성에 15.9시간, 커밋당 약 $0.24(O3-mini 기준)가 소모되었습니다.

실패한 22개 커밋의 원인은 부정확한 버그 패턴(9%), 부정확한 계획(32%), 부정확한 구현(59%)으로 나뉩니다. 특히 buffer-overflow와 use-after-free 유형에서 실패율이 높았는데, 정적 분석 자체가 버퍼 경계 판별이나 멀티스레드 코드 분석에 근본적으로 어려움을 겪기 때문입니다.

#### Checker Refinement
39개 valid checker 중 26개는 바로 plausible로 분류되었고, 나머지 13개 중 11개가 정제를 통해 plausible이 되어 총 37개의 plausible checker를 확보하였습니다(정제 성공률 84.6%). 최종적으로 triage agent까지 적용한 후의 오탐률은 약 32%입니다.

### RQ2: Detected Bugs
KNighter가 합성한 체커들은 리눅스 커널에서 총 92개의 새로운 버그를 발견하였으며, 77개 확인, 57개 수정, 30개 CVE 번호가 할당되었습니다. 평균 버그 잔존 기간은 4.3년이고, 26개는 5년 이상 잠복해 있던 버그입니다. 버그의 대부분(67개)은 drivers 서브시스템에서 발견되었으며, NPD(54개)가 가장 많은 비중을 차지합니다. 39개 커밋에서 생성된 체커가 평균 2.4개의 버그를 발견했고, 5개 이상을 찾아낸 체커도 5개 있어 반복되는 에러 패턴에서 파생된 체커일수록 높은 탐지 수를 보였습니다. <br>

### RQ3: Orthogonality with Smatch
기존의 자동 정적 분석기 생성 도구가 없으므로, 리눅스 커널 분석에 널리 쓰이는 전문가 작성 도구인 Smatch를 비교 대상으로 사용하였습니다. Smatch를 전체 커널에 대해 실행한 결과 1,970개의 에러와 2,870개의 경고를 보고했지만, **KNighter가 발견한 버그는 탐지하지 못했습니다**. 이는 Smatch의 `check_deref` 체커가 일반적인 범위 분석에 의존하는 반면, KNighter는 도메인 특화 지식을 패치로부터 학습하기 때문입니다. 결론적으로 KNighter와 Smatch는 서로 다른 종류의 버그를 탐지하며, KNighter는 기존 도구를 대체하는 것이 아니라 **상호 보완적** 인 역할을 합니다.

### RQ4: Effectiveness of Components
KNighter의 각 구성 요소가 정말 효과적인지 검증하는 부분입니다.

첫째로 **Bug Triage Agent** 의 경우, 39개 valid checker에서 79개 리포트를 샘플링하여 성능을 측정하였습니다. 결과는 TP 7개, FP 22개, TN 50개, FN 0개였습니다. FN이 0이라는 점이 핵심인데, 오탐을 다소 통과시키더라도 실제 버그를 놓치지 않는다는 의미이므로 보안 분석 맥락에서 중요합니다. 다수결 투표(majority voting) 방식도 실험했지만 유의미한 개선은 없었습니다.

둘째로 **Ablation Study** 에서는 20개 커밋을 대상으로 세 가지 설계 선택을 검증하였습니다.

- **Multi-stage vs Single-stage**: 3단계 합성(12개 valid)이 단일 단계(8개 valid)보다 효과적이며, 단일 단계는 구문 에러도 거의 두 배(52 vs 28)로 많았습니다. 복잡한 작업을 하위 단계로 분해하는 것이 LLM 성능 향상에 효과적임을 보여줍니다.
- **고정 예제 vs RAG**: RAG 기반 동적 예제 선택도 동일하게 12개 valid checker를 생성했지만, 토큰 비용이 약 2배로 증가하여 비용 대비 고정 예제가 더 효율적이었습니다.
- **LLM 모델 비교**: O3-mini(12개)가 가장 우수했고, GPT-4o와 DeepSeek-R1(각 11개)이 근접했습니다. Gemini-2-flash는 4개에 그쳤는데, 존재하지 않는 CSA API를 빈번하게 사용하여 구문 에러가 130개에 달했습니다. 체커 합성에는 일반적인 코딩 능력뿐 아니라 **타겟 프레임워크의 API에 대한 정확한 지식이 필수적** 임을 시사합니다.

## Limitations and Discussion
### Limitations
KNighter는 use-after-free처럼 상태 기계 추론이 필요한 복잡한 버그 패턴이나, 멀티스레드 코드와 락 분석이 요구되는 동시성 이슈에서 어려움을 겪습니다. 이는 현재 LLM이 프로그램의 시간적·프로시저 간 동작을 정교하게 이해하는 데 한계가 있기 때문입니다. 향후 방향으로는 복잡한 버그 리포트를 형식적인 상태 기계 표현으로 자동 추상화하거나, 지나치게 복잡한 패치를 필터링하고 재사용 가능한 고품질 패치만 선별하여 학습하는 방법이 제안되었습니다.

### Generability
KNighter의 3단계 워크플로우(패치로부터 체커 합성 → 패치 기반 검증 → 트리아지/정제)는 리눅스 커널에 한정되지 않습니다. 버그 수정 커밋이 있는 버전 히스토리와 정적 분석 프레임워크만 갖추면 다른 프로젝트에도 적용 가능하며, C/C++ 외에도 few-shot 예제를 바꾸면 CodeQL이나 Semgrep 같은 다른 분석 프레임워크로도 확장할 수 있습니다.
