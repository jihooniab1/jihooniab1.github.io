## Introduction
AI 에이전트는 LLM이 외부 환경과 상호작용할 수 있도록 다양한 tool을 연결함으로써 LLM의 기능을 확장합니다. 이 과정에서 AI 에이전트는 다양한 외부 소스의 데이터를 처리하는데, 여기에는 **신뢰할 수 있는 데이터(예: 댓글 작성자)** 와 **공격자가 제어할 수 있는 데이터(예: 댓글 내용)** 가 모두 포함될 수 있습니다. 

AI 에이전트 보안에 대한 앞선 연구들은 주로 **indirect prompt injection(IPI)** 에 집중되어 있는데, 제일 많이 연구된 분야는 **instruction injection** 으로, 공격자가 제어하는 데이터가 instruction으로 잘못 해석되게 하는 공격입니다. 이에 대응하여 `model hardening`, `input guardrails`, `dual-LLM` 등 여러 방어 기법이 제안되었고, 이 방어 기법들의 핵심은 **에이전트 데이터로부터 instruction을 분리** 하여 공격자가 제어하는 데이터가 에이전트의 행동에 영향을 미치지 못하도록 막는 것입니다.

본 논문에서는 새로운 유형의 IPI 공격인 **ADI** 를 소개합니다. ADI는 trusted data와 untrusted data 사이의 격리가 부족하다는 취약점을 활용하여 **untrusted data를 trusted data인 것처럼 LLM이 오인하도록** 합니다. 이를 위해 ADI는 **probabilisitc delimiter injection** 공격 기법을 이용합니다. JSON의 `{}`와 같은 delimiter를 untrusted field에 주입하여, 공격자는 LLM의 자료 구조 해석을 오염시키고 공격자가 제어하는 데이터를 믿을 수 있는 메타데이터로 속일 수 있습니다. LLM은 데이터를 **확률적으로** 해석하기 때문에, SQL 인젝션이나 XSS와 달리 파서가 거부할 만큼 부정확한 delimiter라도 LLM은 이를 유효한 구조적 delimiter로 오해할 수 있습니다.

본 논문에서는 세 가지 실제 공격을 통해 ADI를 시연합니다. 첫 번째는 웹 에이전트를 대상으로 하는 임의 클릭 공격으로 가짜 UI 요소가 에이전트로 하여금 공격자가 특정해둔 요소를 클릭하게 만들어 XSS와 유사한 공격을 수행하는 것입니다. 두 번째는 코딩 에이전트를 대상으로 하는 원격 코드 실행 공격으로, 공격자가 깃허브 issue 커멘트를 마치 메인테이너가 작성한 것처럼 스푸핑하여 에이전트가 악의적인 커맨드를 수행하게 합니다. 세 번째는 가짜 tool response를 주입하여 에이전트가 실제 코드를 리뷰하지 않고 풀 리퀘스트를 머지하게 만드는 공급망 공격입니다. 평가 결과 최신 LLM 모델들이 ADI 공격에 취약한 것을 확인할 수 있었고, 기존 IPI 방어 기법들은 ADI에 효과적으로 대응하지 못함을 확인했습니다. 

## Background
### Agent Context in AI Agents
#### AI Agents
![a1](/assets/img/posts/papers/adi_1.png) <br>
AI 에이전트는 **에이전트 컨텍스트** 를 유지하는데, 에이전트 컨텍스트는 주어진 작업과 관련된 모든 정보(사용자 프롬프트, tool response 등)를 담고 있습니다. 사용자가 프롬프트를 입력하면(**"1"**) 에이전트는 이를 에이전트 컨텍스트에 추가한 뒤 LLM에 전달하여 응답을 받습니다(**"2"**). LLM이 tool 호출을 결정하면 에이전트가 해당 tool을 실행하고(**"3"**), tool은 외부 환경과 상호작용한 후(**"4"**) 그 결과를 에이전트 컨텍스트에 반환합니다(**"5"**). 에이전트는 LLM이 작업 완료를 판단할 때까지 **2-5** 루프를 반복하며, 최종적으로 결과를 사용자에게 반환합니다(**"6"**).

#### Agent Context
에이전트 컨텍스트는 크게 **instruction** 과 **agent data** 두 가지로 구성됩니다.

**Instruction** 은 LLM의 행동을 유도하는 역할을 하며, 에이전트의 행동 방식, tool 설명, 안전 가이드라인 등을 정의하는 **system prompt** 와 사용자가 요청한 작업인 **user prompt** 로 나뉩니다.

**Agent data** 는 에이전트 실행 중 생성되거나 수집된 데이터를 말합니다. Agent data는 에이전트의 행동을 직접 제어하도록 설계된 것은 아니지만, LLM의 판단에 컨텍스트를 제공함으로써 간접적으로 에이전트의 행동에 영향을 미칩니다. <br>

![a2](/assets/img/posts/papers/adi_2.png) <br>

에이전트가 LLM을 호출할 때 agent data는 LLM이 올바르게 해석할 수 있도록 JSON, Markdown, XML 등 구조화된 형식을 갖춰야 합니다. 이 형식의 핵심 요소가 바로 **delimiter(구분자)** 입니다. Delimiter는 agent data의 구성 요소들을 분리하는 문자 시퀀스로, 세 가지 수준의 구조를 구분합니다. 첫 번째는 **tool call block** 으로, 각 블록은 tool 호출과 그에 대응하는 응답으로 구성됩니다. 두 번째는 **object** 로, tool call block 내부의 개별 데이터 항목(이메일, 파일 등)을 나타냅니다. 세 번째는 **field** 로, object 내의 개별 데이터 속성을 나타냅니다.

위 그림은 Claude의 데이터 형식을 단순화한 예시입니다. Tool call block 수준에서는 `<call>` 과 `<results>` 태그가 tool 호출과 응답을 구분하고, object 수준에서는 `{` 와 `}` 가 개별 데이터 항목을 구분하며, field 수준에서는 `:` 과 `"` 가 필드 이름과 값을 구분합니다.

### Indirect Prompt Injection Attack
![a3](/assets/img/posts/papers/adi_3.png) <br>

IPI 공격은 에이전트의 system prompt나 user prompt를 직접 조작할 수 없는 원격 공격자를 가정합니다. 대신 공격자는 에이전트가 tool을 통해 수집하는 **외부 자원(이메일, 웹 페이지, 깃허브 이슈 커멘트 등)에 악성 데이터를 삽입** 하여 agent data를 부분적으로 제어합니다. 이를 통해 에이전트의 행동을 사용자의 의도와 다르게 유도할 수 있습니다.

IPI 공격의 근본 원인은 에이전트 컨텍스트 내에서 instruction과 agent data가 명시적인 경계 없이 혼재한다는 점입니다. LLM의 확률적인 특성으로 인해, 공격자가 에이전트 컨텍스트에 악성 데이터를 주입하면 LLM이 이를 다른 구성 요소로 오인하여 에이전트가 의도하지 않은 행동을 수행하게 만들 수 있습니다.

IPI의 가장 대표적인 유형은 **instruction injection** 으로, 공격자가 조작한 데이터를 LLM이 instruction으로 잘못 해석하게 만드는 공격입니다.

## Agent Data Injection Attack
### Threat Model
에이전트는 tool을 이용하여 이메일, 웹 페이지 등 **제3자가 제공하는 외부 자원과 상호작용** 합니다. 위협 모델 상에서 에이전트, tool, 제3자 서비스는 모두 정상적으로 구현되어 있지만, 이러한 서비스들은 공격자가 작성한 콘텐츠(이메일, 리뷰 커멘트 등)를 호스팅할 수 있습니다. 에이전트의 보안 목표는 외부 콘텐츠와 무관하게 사용자의 의도에 부합하는 행동을 유지하는 것입니다.

공격자는 에이전트, system prompt, user prompt를 직접 조작할 수 없지만, 에이전트가 나중에 조회할 외부 자원에 콘텐츠를 작성할 수 있습니다. 공격자는 대상 에이전트가 사용하는 데이터 형식을 사전에 파악하고 있으며, 목표는 에이전트가 사용자의 의도와 다른 행동을 수행하도록 유도하는 것입니다. 

### Attack Definition and Formalization
이전의 IPI 공격들은 instruction과 에이전트 데이터 사이의 격리 부족을 취약점으로 이용하지만, ADI는 에이전트 데이터 내의 trusted, untrusted data 간 격리 부족을 이용합니다. 본 논문에서는 에이전트 데이터를 $D = (D_T, D_U)$로 나타내고, 이때 $D_T$는 trusted data, $D_U$는 unstrusted data를 의미합니다. 

Trusted data $D_T$는 내부 로직에 따라 tool이나 에이전트 스스로가 만들어내는 데이터로, 이메일을 예로 들면 `sender` 필드나 `url` 필드, 그리고 tool call block의 tool 이름을 trusted data라고 할 수 있습니다. $D_T$는 LLM이 환경을 올바르게 해석하고 정확한 결정을 내리기 위해 의존하는 보안 암초? 역할을 한다고 볼 수 있습니다. 

Untrusted dadta $D_U$는 공격자에 의해 직/간접적으로 제어될 수 있는 데이터로, 이메일 본문이나 웹 페이지의 댓글 같은 유저-생성 컨텐츠 등을 예로 들 수 있습니다. 공격자가 $D_U$를 마음대로 조작할 수 있기 때문에, LLM은 충분한 검증 없이 이 데이터에 의존하여 민감한 결정을 내려서는 안됩니다. <br>

![a2](/assets/img/posts/papers/adi_2.png) <br>

위의 예제 이메일 tool call block에서 trusted data와 untrusted data가 혼재 되어 있습니다. Tool call block 레벨에서는 `get_emails`와 같은 tool name이, email 객체 내에서는 `email_id` 같은 키들이 $D_T$에 속합니다. 이메일 서비스 백엔드가 생성하는 값인 `email_id`와 `sender`의 필드 값은 $D_T$지만, `subject`와 `body`의 값은 $D_U$에 속합니다. 

ADI를 공식으로 표현해보자면 다음과 같습니다. 에이전트 컨텍스트는 instruction $I$와 에이전트 데이터 $D= (D_T, D_U)$의 조합으로 이뤄지며 LLM 호출은 $LLM(I,D)$로 표현됩니다. IPI는 데이터 $D_A$를 $D_U$에 주입하고 이를 $D_U||D_A$로 나타냅니다. Instruction injection 공격의 경우, 공격에 성공하는 경우 다음과 같은 식으로 이어지게 됩니다. **I와 D 사이의 격리가 부족** 할 때 $D_A$가 $I$에 적용된 것과 유사한 결과로 이어진다는 뜻입니다.

$LLM(I, (D_T,D_U||D_A)) \approx_{II} LLM(I||D_A, (D_T,D_U))$

ADI 공격은 LLM이 $D_A$를 $D_T$의 일부처럼 잘못 해석하게 만들어 $D_A$가 $D_T$에 적용된 것과 거의 유사한 결과를 얻는 것을 목표로 합니다. 즉 **$D_T$와 $D_U$ 사이의 격리 부족** 을 이용하는 것입니다. 

$LLM(I,(D_T,D_U||D_A)) \approx_{ADI} LLM(I,(D_T||D_A,D_U))$

이전의 공격은 LLM이 $D_A$를 $I$의 일부로 다루게 만들어 LLM이 사용자가 아니라 공격자가 주는 작업을 수행하게 하지만, ADI 공격은 LLM이 $D_A$를 $D_T$의 일부로 다루게 만들어 사용자의 작업을 수행하면서도 공격자가 제어할 수 있는 데이터를 이용하게 만듭니다. 이 때문에 $D_A$를 $I$로 잘못 해석하게 만드는 방어 기법들이 ADI를 상대로 효과적이지 않습니다. 

### Attack Mechanism
구분자들은 에이전트 데이터 내부의 구조적인 경계를 정의하여 tool call block, object, field level 내부의 엔트리들을 구분합니다. 또한 LLM이 구분자를 올바르게 해석하여 trusted, untrusted data도 구별할 수 있습니다. 

**Probabilistic delimiter injection** 은 ADI의 핵심 공격 기법으로, 공격자는 LLM이 데이터 구조를 잘못 해석하도록 untrusted data 필드에 `probabilistic delimiter`를 주입합니다. `Probabilistic delimiter`는 공격자가 주입하는 문자 나열로 tool은 평문으로 다루지만 LLM은 구조적 구분자로 잘못 해석합니다. 그 결과 LLM이 보는 데이터 구조가 실제 데이터와 달라지게 되면서 공격자가 주입한 데이터가 trusted data로 해석될 수 있게 됩니다. LLM은 결정적인 파서와 다르게 데이터를 확률적으로 해석하기 때문에, 문법적으로 정확하지 않은 구분자들도 LLM이 유효한 구분자라고 해석할 수 있습니다. <br>

![a4](/assets/img/posts/papers/adi_4.png) <br>

공격자는 body 필드에 probabilistic delimiter를 포함하는 악성 페이로드를 넣어 이메일을 전송합니다. 실제로는 `attacker@gmail.com`이 보낸 메일의 body 필드에 페이로드가 주입된 것이지만, LLM은 probabilistic delimiter를 구조적인 경계로 해석하여 `alice@gmail.com`이 보낸 두번째 메일이 있었다고 판단하게 됩니다. 

## ADI Attacks against Real-World Agents
### Arbitrary Click Attack via Element ID Injection
이 섹션에서는 웹 에이전트 내의 ADI 취약점을 이용하여 임의 클릭 공격을 수행할 수 있음을 보입니다. XSS 공격은 웹 페이지에 악성 스크립트를 주입하여 피해자의 브라우저에서 이를 실행하는 반면, ADI는 웹 페이지에 악의적인 컨텐츠를 주입하여 에이전트가 공격자가 원하는 행동을 실행하게 만듭니다. 본 논문에서는 이 취약점이 Claude in Chrome, Antigravity, Nanobrowser를 포함하여 실제 웹 에이전트에서도 존재함을 확인하였습니다. <br>

![a5](/assets/img/posts/papers/adi_5.png) <br>

위 그림은 웹 에이전트가 웹페이지를 처리하는 과정을 다루고 있습니다. 사용자가 웹 에이전트에게 이커머스 사이트에 있는 상품 리뷰 요약을 요청하면(**"1"**), 에이전트는 `read_page` tool을 호출하여 웹페이지 컨텐츠를 가져옵니다(**"2"**). `read_page`는 HTML을 처리하여 i) 웹 페이지 요약과 ii) 식별자와 DOM element 간의 매핑 두 가지를 생성합니다. HTML tag를 뽑아내고 안 보이는 컨텐츠를 제거한 다음, 버튼이나 링크 같은 상호작용, 볼 수 있는 텍스트 컨텐츠(`<p>`,`<span`)와 같이 남아있는 element에 고유한 식별자를 할당합니다. 예를 들어 `<button id="next">Next Page</button>`과 같은 버튼 element는 **"Next Page" [ref_7]** 로 요약됩니다.
